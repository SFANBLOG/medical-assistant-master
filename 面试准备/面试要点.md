## 1. 项目一句话与背景

**一句话**：面向医院信息系统教学场景（参考安医大医疗系统用户角色划分）的医疗知识库智能问答平台，基于 **RAG（检索增强生成）** 提供可追溯的医学问答，并带患者/医护/管理的业务功能。

**背景要点**：
- 医疗信息化是医院管理与患者服务的核心，HIS 有明确角色划分（患者、医生、护士、管理员…）。
- 定位：数据库/软工课程设计、教学演示、医疗科普。
- 规模：12 个疾病知识库（公开 242 篇 + 私有 241 篇文档）、5 种角色。

**为什么选 RAG 而不是纯大模型？**
- 纯 LLM 会「编造」且无来源，医疗场景必须**可追溯、不编造**。
- 私有知识库内容大模型没训练过，RAG 把检索到的资料作为上下文喂给模型，回答「有据可依」。

## 3. 系统架构

**分层**：API 层（鉴权+路由）→ Service 层（业务逻辑）→ 数据层（MySQL 结构化 + Milvus 向量 + 磁盘文件）。

## 4. RAG 智能问答核心（最重要）

### 4.1 全流程
1. 提问 → `POST /api/chat/stream/<conv_id>`（SSE，body 携带 question/kb_id）；
2. 鉴权拿 `g.user`，确定角色；
3. **定可见范围**：retriever 内 `_get_visible_kb_ids(role, user_id, kb_id)`（医生/管理员可含私有，其余仅公开）；`kb_id` 空则跨全部可见库检索；
4. **双路召回 + 融合重排 v4**（BM25∪BGE 各 Top-30 → 加权打分 ≥0.45）→ Top-8 切片；
5. 拼 `SYSTEM_PROMPT + context` → 大模型流式生成；
6. 持久化 messages + citations，SSE 返回 `meta → delta×N → done`；
7. 前端 `ReadableStream` 逐帧渲染 + 引用来源。

### 4.2 混合检索与重排（retriever.py v4）——核心加分点
解决「纯向量召回相似度失真 / 同义词不一致 / 检索质量不稳定」：
1. **BM25 稀疏召回**（jieba 分词，词频统计落库 `bm25_terms`），关键词精确匹配必进候选；
2. **BGE 稠密召回**：语义近似片段进候选；双路各取 **Top-30 并集去重**（候选 40~60 条）；
3. **融合重排 v4**：`score = 0.55·稠密 + 0.30·BM25 + 0.15·词法重叠`；实体命中额外地板 `0.90 + 0.10×证据数`；**≥0.45 且仅 approved&ready 文档** → Top-8 进入上下文；
4. **评测**：本地 42 问 Hit@1=100%、平均分≈0.94（旧实现 1/(1+d) 压分失真已改为 cosine 相似度修正）。

### 4.3 SSE 流式输出
- 后端 Flask 生成器 `yield "data:{...}"`，`Response(mimetype='text/event-stream')`。
- 前端原生 `fetch` + `ReadableStream` 分帧解析，逐字符更新。
- **坑**：生成器在应用上下文外运行，需提前捕获 DB 配置，用独立连接 `new_conn` 并在 finally 关闭，避免跨线程共享连接。

### 4.4 引用溯源
`conversation → message → citations → documents`，`CitationCard` 展示 source_text/title/similarity，回答可追溯。

## 5. 公开/私有权限模型

知识库、文档都有 `visibility`（public/private）；文档落到 `uploads/<库>/公开|私有/`。

| 角色 | 创建库 | 传公开 | 传私有 | 查公开 | 查私有 |
| --- | :-: | :-: | :-: | :-: | :-: |
| 患者/护士/群众 | ❌ | ❌ | ❌ | ✅ | ❌ |
| 医生 | ✅ | ✅ | 仅自己库 | ✅ | ✅ |
| 管理员 | ✅ | ✅ | ✅ | ✅ | ✅ |

**实现**：
- 后端写接口统一 `@login_required` + `@role_required("doctor","admin")`；`kb_service` 按 role/user_id/uploader_role 过滤可见（admin 任意、doctor 限公开库或自有私有库）；检索侧 `retriever._get_visible_kb_ids(role, user_id, kb_id)` 用 SQL 圈定可见库 ID 列表再交给向量/BM25 检索——私有内容根本到不了召回阶段。
- 前端 `router/index.ts`：`meta.roles` + 路由守卫。**双端都控制**（前端只是体验，后端才是安全边界）。

**RAG 系统独有安全点**：不只控制"能否看页面"，还控制"AI 检索时能否碰私有文档"，否则私有内容会通过回答泄露。

## 6. 向量存储与检索优化

- **Milvus 设计**：单集合 `medical_chunks`，`kb_id` 作**分区键**；字段 `doc_id/chunk_index/filename/visibility/text/vector(768)`；**HNSW + COSINE**。
- **统一接口 + 兜底**：`rag/vectorstore.py` 的 `get_vectorstore()` 模块级单例；Milvus 不可用自动降级 **NumpyStore**（numpy 暴力 cosine + JSON/npy 落盘），`distance=1-cos`，语义一致。
- **Embedding**：本地 `bge-base-zh-v1.5`（768 维），或远程 `/embeddings`；留空用**确定性哈希向量**兜底。
- **维度自动校验**：读模型 `config.json` 的 `hidden_size` 校正 `EMBED_DIM`，两端都做维度检查。

**追问准备**：为什么 cosine 而非 L2？→ 只关心方向/语义相似；本项目已 L2 归一化，cosine=点积。HNSW？→ 基于图的 ANN 索引，用 M/efConstruction 平衡速度与召回。

## 7. 文档上传与切分

- 支持 `txt/md/pdf/docx/pptx`，≤20MB；落盘 `uploads/<库>/公开|私有/<uuid>_<name>`。
- **状态机**：`processing → ready(待复核) → approved / rejected / failed`；失败不抛 500，返回带 `error` 的行，前端展示原因并允许删除；未复核/驳回文档不进入检索上下文。
- **中文切分**（`rag/chunker.py: chunk_document`）：先按标题层级把文档切成**章节**，章节内再按**句子聚合**到 CHUNK_SIZE=500；相邻块不用字符硬截断，用**整句回填** overlap=80，避免切断词句。
- 切分 → `embedder.embed` → `vectorstore.insert_batch` → 更新 `chunk_count`。

## 8. 数据库设计

- MySQL 8，库 `medical-assistant-master`，后端启动自动建库建表（`schema_mysql.sql` 幂等），首启播种（5 角色 + 12 库 241 文档 + 每表 ≥50 条）。
- **17 张表**：11 张业务表（users、knowledge_bases、documents、conversations、messages、citations、hospitalizations、bills、appointments、nursing_records、schedules）+ 4 张检索支撑表（chunks、sub_chunks、bm25_terms、chunk_vectors）+ audit_logs 审计表 + appointment_requests 预约复核表。
- **索引**：外键字段都建索引，`bill_no` 唯一键。
- **兼容层**：`db.py` 定义 `Row`（同时支持 `row["col"]/row[0]/dict(row)`），`MysqlConn` 把 `?` 自动转 `%s`，一套代码跑两种数据库；`DB_TYPE=sqlite` 本地兜底。
- **连接管理**：请求作用域 `get_conn`（flask.g），SSE 用独立连接 `new_conn`，避免长连接跨线程。

## 9. 认证与安全

- **JWT（HS256）**，payload：`user_id/username/role/iat/exp`，24h。
- **密码哈希**：`werkzeug generate_password_hash/check_password_hash`（加盐），不存明文。
- **双端鉴权**：前端路由守卫（体验）+ 后端 `@login_required`（JWT 解析 → 注入 g.current_user）/ `@role_required(...)`（角色白名单，越权 403）；业务层再用 role/user_id 实时查库过滤数据归属。
- **最小下发**：登录只返回安全字段，绝不下发 `password_hash`。
- **注意**：生产必须改 `JWT_SECRET`；`.env` 不入库。

## 12. 30 个高频面试问题与回答模板

### A 组 · 项目概述（1-5）

**Q1. 讲讲你的项目是做什么的？**
> 基于 RAG 的医疗知识库问答平台，技术栈 Vue3 + Flask + MySQL + Milvus。内置 12 个疾病知识库共 483 篇文档、5 种角色。核心是按角色做公开/私有权限隔离检索，再通过检索增强生成回答，带引用溯源；并带住院、消费、挂号、护理、排班等医院业务功能。

**Q2. RAG 的完整流程？**
> 提问 → 鉴权 → 按角色确定可见检索范围 → BM25∪BGE 双路召回 → 融合重排 v4（≥0.45）→ Top-8 切片 → 拼系统提示词 → 大模型流式生成 → 持久化引用 → SSE 返回。前端流式渲染并展示引用来源。

**Q3. 为什么用 RAG 不用纯 LLM？**
> 医疗场景要求不编造、可追溯。RAG 把检索到的资料作为上下文给模型，模型只能"有据可依"地回答并给出引用，避免幻觉。

**Q4. 项目有哪些角色？权限怎么划分的？**
> 5 种：患者/医生/护士/群众/管理员。核心差异在：能否创建知识库、能否检索私有文档、能否系统管理。医生/管理员可查私有并建库上传，患者/护士/群众只能查公开。

**Q5. 项目用了哪些技术？为什么选它们？**
> Vue3（组件化/生态）+ Element Plus（成熟 UI）+ Flask（轻量/易快速开发，配合 Python 的 AI 生态）+ MySQL（关系数据）+ Milvus（百万级向量检索）+ OpenAI 兼容接口（模型可替换）+ bge embedding（中文语义好）。

### B 组 · RAG 与检索（6-14）

**Q6. 混合召回具体怎么做的？**
> 双路召回 + 融合重排 v4：①稠密——`embedder.embed` 编码问题后 `vs.search` 按可见库 cosine 召回 Top-30；②BM25 稀疏——`_expand_query` 同义词扩展（发烧→发热、熬夜→失眠）后关键词召回 Top-30；两路并集去重 → `get_reranker().rerank` 融合打分（0.55·稠密 + 0.30·BM25 + 0.15·词法，× 标题/位置/实体增强，min_score=0.45）取 Top-8。

**Q7. 相似度怎么做到 ≥0.95？**
> 融合打分内置"核心实体标题命中"检测：查询主题就是文档主题（标题子串 / 实体词包含 / 同义词双命中）时打高相关度下限 `floor = 0.90 + 0.10*证据分`（即 `final = max(final, floor)`），展示校准后目标文档稳定 ≥0.95。纯向量分低（0.3~0.5）也不拖垮——BM25/词法证据与地板兜底，噪声被 0.45 阈值过滤。

**Q8. 向量库用的什么？降级怎么做？**
> 首选 Milvus（HNSW+COSINE，kb_id 分区）。统一接口封装在 `rag/vectorstore.py`，`get_vectorstore()` 做单例选择，Milvus 连不上自动降级 NumpyStore（纯 numpy cosine），语义一致，始终可用。

**Q9. 中文文本怎么切分？为什么这样切？**
> 先按 Markdown 标题层级把文档切成**章节**，再在章节内把句子聚合到 CHUNK_SIZE=500（中文约 1 字/token，低于 bge 的 512 token 上限）；相邻块不按字符硬截断，用**整句回填** overlap=80 保留上下文，避免把词句拦腰切断。

**Q10. 提问中的疾病/主题怎么判定？**
> 在融合重排内部完成：`reranker` 的医学实体词典 `_MEDICAL_ENTITIES`（实体 + 同义词组）从提问中匹配已知实体（泛化词剔除），`_core_entity_match` 再判定该实体是否就是文档标题主题（标题子串 / 实体词包含 / 同义词组双命中）。这样"中暑的急救处理"能判定主题=中暑，命中《中暑急救》类文档标题 → 直接进入高相关度地板。

**Q11. 同义词问题怎么处理？**
> 检索入口统一处理：`retriever._MEDICAL_SYNONYMS` 维护医疗同义词组（发烧→发热、中风→脑卒中、熬夜→失眠…），`_expand_query` 对提问先做同义词扩展（按医学主题分类取词）再走 BM25 召回；稠密路靠 bge 语义近似天然覆盖同义改写。

**Q12. 选错知识库导致答不对怎么办？**
> 后端在 `kb_id` 为空/0 时跨当前用户可见的**全部知识库**检索，选中库只做轻微加权（+0.02），不限定单一库，避免选错。这是"解决选错库"的设计。

**Q13. 引用溯源怎么做的？**
> 每次回答把命中的切片存到 `citations` 表（document_id, chunk_index, source_text, title, similarity），前端 `CitationCard` 展示，点击可看来源。链路 conversation→message→citations→documents。

**Q14. 如果检索不到相关内容怎么处理？**
> 检索链路两道过滤：①稠密路 `DENSE_MIN_SIMILARITY`（默认 0.0）只滤明显噪声；②融合重排 `RERANK_MIN_SCORE=0.45`，低于阈值视为无关不进上下文；若最终无可参考内容，模型按系统提示词如实说明"资料未覆盖"，离线兜底也会提示"未检索到相关内容"。

### C 组 · 权限与安全（15-19）

**Q15. 公开/私有权限怎么防止私有内容泄露？**
> 在检索层而非仅前端控制：检索范围由 `_get_visible_kb_ids(role, user_id, kb_id)` 决定（患者/护士/群众只能圈到公开库），可见库 ID 列表再传给向量/BM25 检索，私有向量根本不进回答上下文。后端权限校验是安全边界，前端路由守卫只是体验。

**Q16. JWT 认证流程？**
> 登录校验密码哈希（PBKDF2 加盐）→ 签发 HS256 JWT（payload：user_id/username/role/iat/exp）→ 前端存 localStorage → 请求带 Bearer → 后端 `login_required` 解析注入 `g.current_user`；写接口再叠加 `role_required("doctor","admin")` 白名单（越权 403）。401 前端自动登出。

**Q17. 密码是怎么保存的？**
> 用 werkzeug 的 `generate_password_hash`（PBKDF2 加盐哈希）存储，校验用 `check_password_hash`，数据库不存明文，登录接口也不下发 password_hash。

**Q18. 前端怎么控制权限？**
> `router/index.ts` 每条路由定义 `meta.roles`，`beforeEach` 守卫校验 token 存在和角色是否在允许列表，不满足则重定向。配合 Pinia 存的用户角色渲染不同左侧导航。

**Q19. 怎么保证前后端权限一致？**
> 前端路由守卫只是提升体验，真正的安全在**后端**：写操作接口用 `@login_required` + `@role_required("doctor","admin")` 限定角色；知识库/文档按角色与归属过滤可见（`kb_service` 接收 role/user_id，admin 任意、doctor 限公开库或自有私有库）；检索侧由 `retriever._get_visible_kb_ids` 圈定范围。前端绕过不了后端。

### D 组 · 数据库与存储（20-24）

**Q20. 数据库有几张表？关系怎么设计的？**
> 17 张：11 张业务表（用户/知识库/文档/会话/消息/引用/住院/账单/挂号/护理/排班）+ 4 张检索支撑表（chunks/sub_chunks/bm25_terms/chunk_vectors）+ audit_logs 审计 + appointment_requests 预约复核表。核心链路：users → conversations → messages → citations → documents；外键都建索引。

**Q21. 数据库怎么实现自动建库建表？**
> `app.py` 启动 → `db.init_schema`：若 MySQL，先 `CREATE DATABASE IF NOT EXISTS`，再执行 `schema_mysql.sql`（全部 `IF NOT EXISTS` 幂等）；首启 user 表为空时自动播种。

**Q22. 一套代码怎么同时支持 MySQL 和 SQLite？**
> `models/db.py` 抽象出 `Row`（兼容列名/下标/dict）和连接封装，把 SQLite 的 `?` 占位符自动转成 MySQL 的 `%s`；SQL 用标准语法，通过 `DB_TYPE` 切换。SSE 用独立连接。

**Q23. 播种演示数据怎么做的？为什么幂等？**
> `seed.py` 的 `seed_all`：先查 user 表，为空才播种；5 角色账号、12 知识库 240 文档、每表 50+ 条。幂等设计保证重启不会重复插入。

**Q24. Milvus 集合是怎么设计的？**
> 单集合 `medical_chunks`，`kb_id` 作分区键隔离知识库，字段含 doc_id/chunk_index/filename/visibility/text/vector，用 HNSW + COSINE 索引。visibility 字段用于公开/私有过滤。

### E 组 · 流程与部署（25-27）

**Q25. SSE 流式响应怎么实现？遇到什么坑？**
> 后端 Flask 生成器逐帧 `yield "data:{...}"`，mimetype='text/event-stream'。前端用 fetch 读 ReadableStream，按 `\n\n` 分帧、`data:` 解析。坑：生成器在应用上下文外运行，不能访问 current_app，需提前捕获 DB 配置并用独立连接，避免跨线程共享连接。

**Q26. 项目怎么部署的？**
> 本地可分别起前后端；生产用 Docker Compose：mysql、etcd/minio/milvus、backend(gunicorn)、frontend(Nginx)。服务间用健康检查 `depends_on condition: service_healthy` 控制启动顺序，数据用命名卷持久化。

**Q27. 启动流程是怎样的？**
> `python backend/app.py` → 加载 .env 配置 → init_schema 建库建表 → 注册蓝图/错误处理/CORS → 注册健康检查 → 首启自动播种 → 起 gunicorn/开发服务器监听 8010。前端 dev 代理 /api 到 8010。

### F 组 · 优化与设计思考（28-30）

**Q28. 这个项目有哪些值得讲的工程点？**
> ①全链路降级（MySQL↔SQLite、Milvus↔Numpy、在线LLM↔离线、bge↔哈希）；②RAG 混合召回解决选错库/低分/同义词；③检索层权限隔离防私有泄露；④文档状态机 + 失败可控；⑤向量维度自动校验；⑥幂等播种。

**Q29. 如果文档很多（如 100 万篇），哪里会是瓶颈？怎么优化？**
> 瓶颈：同步入库阻塞、NumpyStore 暴力检索、检索精度。优化：入库异步化（队列）+ 分批；向量用 Milvus（已用）+ 调 HNSW 参数；加 BM25+向量 hybrid 与 Rerank 提升精度；embedding 缓存；检索结果分页/漏斗。

**Q30. 如果让你重构这个项目，你会怎么做？**
> ①后端改 FastAPI（异步 + 类型提示 + OpenAPI）；②入库用任务队列异步化；③检索引入 Rerank（bge-reranker）与 hybrid search；④多轮上下文 + 流式中止；⑤加单元测试与 CI；⑥生产安全：密钥管理、限流、防 prompt 注入；⑦前端拆组件/加虚拟列表、封装 SSE 客户端。

## 13. 可能的追问与项目不足（诚实回答）

### 可能被追问的坑
- **JWT_SECRET 是 dev 默认值**：`config.py` 有明文兜底，生产必须改——主动提展示安全意识。
- **API key 写死**：`config.py` 有默认 `OPENAI_API_KEY`，应只走环境变量。
- **NumpyStore 是暴力检索**：数据量大性能差，只是兜底。
- **哈希向量语义差**：配置错会静默低分检索，代码已加醒目告警。

### 可主动提出的改进方向
1. **异步化**：文档入库目前同步，会阻塞请求；可改 Celery/RQ 后台异步 + 轮询状态。
2. **检索更工程化**：对比 BM25+向量 hybrid（Milvus HybridSearch/RRF），加 Rerank（bge-reranker）提升精度。
3. **流式优化**：封装通用 SSE 客户端，支持 AbortController 中止请求。
4. **多轮上下文**：拼接历史消息做多轮对话。
5. **性能与缓存**：调 HNSW 参数（M/efConstruction/ef）；embedding 结果缓存。
6. **安全加固**：限流、防 prompt 注入、文件上传真实类型嗅探。
7. **测试与监控**：补 retriever 单元测试、日志/指标监控、相似度阈值参数化。
8. **前端优化**：咨询历史/大数据列表分页、虚拟列表。

> 加分技巧：主动指出"上传同步、可加 Rerank、生产换密钥"，比等面试官挑毛病显得更懂工程。
