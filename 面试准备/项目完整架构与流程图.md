## 第 2 阶段 需求分析与角色定义

### 2.1 需求来源
- 医疗信息化是医院管理与患者服务的核心支撑，参考 **HIS（医院信息系统）** 的实际角色划分（安医大医疗系统用户角色）。
- 需要把本地医学知识库转化为**可检索、可追溯**的智能问答，而不是依赖大模型的"编造"。

### 2.2 角色与权限需求

```mermaid
flowchart TD
    subgraph "五种角色"
        P["患者 patient"]
        D["医生 doctor"]
        N["护士 nurse"]
        Pub["群众 public"]
        A["管理员 admin"]
    end
    subgraph "核心能力差异"
        C1["能否创建知识库/上传文档"]
        C2["能否检索私有文档"]
        C3["能否看全系统看板/管理用户"]
    end
    P --> C1 & C2 & C3
    D --> C1 & C2 & C3
    N --> C1 & C2 & C3
    Pub --> C1 & C2 & C3
    A --> C1 & C2 & C3
```

| 角色 | 定位 | 权限特点 |
| --- | --- | --- |
| 患者 | 本人健康信息 | 只能查公开库/公开文档，查本人住院/消费/挂号 |
| 医生 | 内容生产者 | 可创建知识库、上传公开/私有文档、检索私有、管理患者/住院/排班 |
| 护士 | 护理执行 | 护理记录/排班，检索仅公开 |
| 群众 | 公众科普 | 仅查公开、健康资讯、挂号 |
| 管理员 | 系统运维 | 用户管理、全部知识库、全系统看板 |

### 2.3 验收标准（从改进文档提炼）
1. 公开/私有权限模型正确（患者/群众/护士看不到私有）。
2. 上传失败能返回具体原因、可处理。
3. RAG 引用相似度 ≥ **0.95**。
4. 数据库自动建库建表，每表预置 ≥50 条数据。
5. 界面统一在单页（Vue），角色导航符合事实。

## 第 3 阶段 系统设计

### 3.1 总体架构

```mermaid
flowchart LR
    U["用户（5 角色）"] --> FE["Vue3 SPA<br/>Element Plus / Router / Pinia"]
    FE -- "HTTP /api + SSE 流式" --> BE["Flask 后端<br/>Blueprint + Service 分层"]
    BE --> AUTH["JWT 认证<br/>login_required / role_required"]
    BE --> RET["rag/retriever.py<br/>混合召回 + 重排"]
    BE --> PIPE["kb_service.py<br/>文档入库（抽取→切分→向量化）"]
    RET --> LLM["rag/llm.py<br/>OpenAICompat / 离线兜底"]
    RET --> VS["rag/vectorstore.py<br/>Milvus / NumpyStore"]
    BE --> MySQL[("MySQL 8<br/>17 张表")]
    BE --> FS[("uploads/ 文档文件")]
    PIPE --> VS
    LLM --> EXT["外部 大模型 / bge embedding"]
```

### 3.2 数据库设计（17 张表）
11 张业务表：users / knowledge_bases / documents / conversations / messages / citations / hospitalizations / bills / appointments / nursing_records / schedules；另含 4 张检索支撑表（chunks / sub_chunks / bm25_terms / chunk_vectors）+ audit_logs 审计表 + appointment_requests 预约复核表，共 17 张。

**核心关联（引用溯源链）：**
```text
conversations (会话)
   └─ messages (问答对: role=user/assistant)
        └─ citations (引用来源: document_id, chunk_index, similarity)
             └─ documents (文档: kb_id, file_path, visibility, chunk_count, status)
```

### 3.3 知识库设计
- 12 个疾病知识库，每个含 `公开/` 与 `私有/` 两个文件夹，各 20 篇（另含 3 篇专题增补，共 483 篇入库）。
- 库与文档都有 `visibility`（public/private）。

### 6.1 代码组织（Blueprint + Service 分层）
```

rag/            retriever(混合召回+重排) llm(大模型抽象) vectorstore(Milvus/NumpyStore) chunker embedder reranker bm25
models/         db.py(数据访问) schema_mysql.sql schema.sql
utils/          db(连接池) jwt_utils file_parser file_utils text_utils errors
agent/          orchestrator roles tools memory guardrails（多智能体扩展）
```

### 6.2 RAG 问答核心流程

```mermaid
sequenceDiagram
    participant F as 前端
    participant A as routes/chat_bp.py
    participant S as chat_service
    participant R as retriever
    participant V as vectorstore
    participant L as llm
    participant DB as MySQL

    F->>A: POST /api/chat/stream/<conv_id> {question, kb_id}
    A->>A: login_required 解析 JWT → 注入 g.current_user
    A->>S: chat_service.chat_stream_sse(conv_id, question, kb_id)
    S->>S: 校验会话归属 + 末条问题去重后存库
    S->>R: retrieve(query, role, user_id, kb_id)
    R->>R: dense 召回(embedder.embed→vs.search) + BM25(_expand_query→bm25.search)
    R->>V: vs.search / bm25.search
    V-->>R: 稠密 cosine + BM25 命中候选
    R-->>S: Fusion-v4 融合重排 → TOP_K 切片
    S->>S: build_context + build_citations
    S->>L: chat_stream(messages)
    L-->>S: SSE delta 流
    S->>DB: 持久化 messages + citations
    S-->>F: SSE: meta → delta×N → done
```

### 6.3 混合召回策略（retriever.py）——项目灵魂

```mermaid
flowchart LR
    Q["问题 + 可见文档集合"] --> R1["① 稠密向量召回<br/>embedder.embed + vs.search(cosine)"]
    Q --> R2["② BM25 稀疏召回<br/>_expand_query 同义词扩展 + bm25.search"]
    R1 & R2 --> M["Fusion-v4 融合重排<br/>dense/bm25/词法加权 × 标题/实体增强 + 0.90 地板"]
    M --> T["min_score=0.45 滤噪声 → TOP_K=8"]
```

> 关键机制：核心实体标题命中时打地板 `floor = 0.90 + 0.10*证据分`，即 `final = max(final, floor)`；再经展示校准（rel≥0.90 → 显示 ≥0.95），目标文档恒 ≥0.95、兄弟文档按证据分拉开差距、噪声被 0.45 阈值过滤，满足验收。

### 6.4 文档入库流水线（kb_service → rag 组件）
```text
落盘 → 解析文本 → chunk_document(章节化切分：按标题分章 + 句子聚合 500/80)
→ embedder.embed_batch(向量化) → INSERT documents(status='ready', chunk_count)
→ vs.insert_batch(入库, VectorRecord 关联 doc_id)
（解析失败 → INSERT status='failed' + 记录 error，前端展示并允许删除）
```

## 第 7 阶段 前端开发（Vue3 SPA）

```mermaid
flowchart TD

    D --> E["pages/*: 登录/仪表盘/咨询/健康档案/医护/知识库/系统管理"]
```

**前端要点**：
- 单页应用，5 角色共用一套代码，靠路由 `meta.roles` + 守卫区分权限（前端只是体验，后端才是安全边界）。

- `client.ts` 拦截器：请求统一加 `Authorization: Bearer <token>`；响应 401 自动清 token 跳登录。

## 第 12 阶段 数据全生命周期（一份文档的旅程）

```mermaid
flowchart TD
    A["医生/管理员上传<br/>uploads/<库>/公开|私有/xxx.md"] --> B["kb_service: 解析 → 切分 → 向量化<br/>（解析失败 → INSERT status='failed' 行）"]
    B --> C["INSERT documents 行<br/>status='ready', chunk_count=N"]
    C --> D["vs.insert_batch 写入向量<br/>Milvus / NumpyStore 兜底"]
    D --> E["可检索：范围由角色圈定<br/>_get_visible_kb_ids"]
    E --> F["用户提问 → 按角色过滤可见切片"]
    F --> G["检索命中 → 构建上下文"]
    G --> H["大模型回答 → citations 记录引用"]
    H --> I["前端展示回答 + 引用卡片(可溯源)"]
    E --> J["删除 → kb_service.delete_document(doc_id)<br/>delete_by_doc 清向量 + 删库行（磁盘文件保留）"]
```

**这条链路能讲清"公开/私有如何在检索层生效"**：上传按 `uploads/<库>/公开|私有/` 落盘、documents 行带 `visibility`；检索入口 `retriever._get_visible_kb_ids(role, user_id, kb_id)` 用 SQL 圈定可见库 ID 列表（患者/护士/群众只能圈到公开库），再交给向量/BM25 检索——私有向量根本进不了召回范围。

## 第 13 阶段 面试讲解闭环模板

> 当面试官问"讲讲你整个项目"时，按这个顺序讲（约 2~3 分钟）：

1. **背景**：面向医院信息系统教学场景，参考 HIS 角色划分，做一个医疗知识库智能问答平台。
2. **需求**：5 种角色 + 12 疾病知识库 + 公开/私有权限 + 可追溯问答 + 医院业务功能。
3. **技术栈**：Vue3 + Flask + MySQL + Milvus + RAG（OpenAI 兼容 + bge embedding）。
4. **设计**：Blueprint/Service 分层；17 张表；483 篇文档；Milvus 单集合 + kb_id 分区。
5. **开发**：先搭后端 RAG 链路（混合召回 + 流式），再做前端 SPA；数据自动播种。
6. **难点与解法**：选错库/向量分低 → 跨库检索 + 关键词/字符 + 疾病名标题强匹配（相似度≥0.95）；私有泄露 → 检索层 filter；不可用 → 全链路降级。
7. **验收**：检索准确率、权限隔离、健壮性、自动建库。
8. **可改进**：异步上传、Rerank、多轮上下文、安全加固。
