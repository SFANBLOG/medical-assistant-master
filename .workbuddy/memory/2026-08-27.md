# 2026-08-27 工作日志

## 修复 `docker compose up --build` 失败

根目录执行 `docker compose up --build` 报错并修复，最终整套服务可正常启动。

### 根因与修复
1. **构建失败（核心 bug）**：项目缺失 `Dockerfile.backend` / `Dockerfile.frontend`，compose 在读取 Dockerfile 阶段即失败。
   - 新建 `Dockerfile.backend`（python:3.11-slim + gunicorn）、`Dockerfile.frontend`（node:20 构建 + nginx）、`nginx.conf`（托管 dist 并反代 `/api` → backend:8010）、`wsgi.py`（gunicorn 入口，等价于 `python -m backend` 的 `main()`）、`.dockerignore`。
2. **3306 端口冲突**：宿主机 MySQL 服务（mysqld.exe）占用 3306 → 把 compose 中 mysql 宿主端口改为 `3307:3306`（容器内仍 3306，后端经服务名访问不受影响）。
3. **pymilvus 客户端/服务端不匹配**：服务端 milvus 2.3.4，但 `pymilvus` 被解析为 3.x/2.6.x，且 marshmallow 4.x 移除了 `__version_info__` 导致 import 失败。
   - `requirements.txt` 钉为 `pymilvus>=2.3.0,<2.4.0` + `marshmallow<4.0.0`。
4. **worker 启动卡死**：`collection.load()` 在 gunicorn worker 导入阶段阻塞 → `app.py` 中向量库预热改为后台 daemon 线程。
5. **Milvus 在本 Docker 环境无法完成 collection 加载**（即使全新空集合也 `wait for loading collection timeout`，与之前数据损坏无关，属单机版资源/就绪问题）→ `vectorstore.py` 的 `get_vectorstore()` 加 30s 超时，超时优雅降级到 NumpyStore（RAG 仍可用，已加载 240 条预置向量）。用户确认后删除损坏的 `medical_assistant-master_milvus_data` 卷重建。

### 验证结果
- 6 个容器均 Up，mysql healthy（宿主 3307）。
- `GET /api/health` ok；`admindemo / demo123` 登录返回 JWT；`/api/kb/` 返回知识库列表。
- 前端 `http://localhost:3000` 200，nginx 反代 `/api` 正常。
- 向量库实际走 NumpyStore 兜底（Milvus_ENABLE=1 但加载超时降级）。
