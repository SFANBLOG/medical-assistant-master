
## RAG 检索相关度重构（混合检索 + 重排 + BGE 全链路优化）

### 问题
用户截图反馈：查询"儿童发热需要立刻就医吗?"时，最相关的"儿童发热.md"文档排在第 5 名，相关度仅 14.2%；而不太相关的"小儿肺炎"排第 1 名（42%）。目标：相关度 95%+。

### 根因（3 个致命 bug 联合导致）
1. **`jieba.posseg.cut` 返回值不可解包** → `_extract_keywords` 崩溃回退到 bigram → 产生 50 个垃圾重叠关键词（如"儿童发""童发热"等）→ 词法覆盖率被严重稀释
2. **Cross-Encoder 自动检测失效**：`reranker.py:139` 用 `os.getenv("RERANK_MODEL_PATH","")` 空字符串，忽略了 config.py 的 `"auto"` 默认值 → 永远跳过 CE 加载，只用融合模式
3. **`jieba.lcut` 不存在** → BM25 整个崩溃 → 所有候选 bm25=0 → 融合算法 30% 权重浪费

### 修复内容

#### 文件 1：`backend/rag/reranker.py`（完全重写）
- **修复 jieba 兼容性**：`posseg.cut` 解包加 `isinstance(item, (tuple, list))` 兜底；`lcut` 加 `hasattr` 兜底
- **修复 Cross-Encoder 自动检测**：读 `config.RERANK_MODEL_PATH`（默认 "auto"）；新增 `_auto_detect_ce_model()` 方法在 MODEL_DIR 下递归搜索 bge-reranker 模型
- **重写融合算法 v3**：
  - BGE dense 作为主信号（weight=0.55），BM25=0 时动态重分配权重（80% 给 dense）
  - 多粒度词法匹配：字符 bigram + 词级（jieba）+ 实体级（医学词典）
  - 问题类型感知：`_detect_query_type()` 识别 yes_no/when_to/how_to/what_why
  - 标题/heading 匹配加权：`_title_match_bonus()` 标题含查询关键词时 +3%~25%
  - 答案模式匹配：when_to 问 + 文本含"应立即就医"等 → +20%
  - 实体共现奖励：查询和文本同时出现医学实体对 → 每个 +5%
  - 诚实校准：不再人为拉伸到 [0.30, 1.0]，高分 = 真正相关
- **关键词提取重构**：从暴力枚举子串改为基于医学同义词表的精确匹配，5 个高质量关键词 vs 50 个垃圾词

#### 文件 2：`backend/rag/bm25.py`（兼容性修复）
- `jieba.lcut()` → `hasattr(jieba, 'lcut')` 判断后回退 `list(jieba.cut())`

#### 文件 3：`backend/rag/retriever.py`（同义词表扩展 + 查询改写优化）
- 医学同义词表从 15 条扩展到 **70+ 条**（覆盖发热/体温/人群/症状/动作/urgency/感染/过敏等）

## Docker 全栈零报错修复（2026-08-31）

### 现象
`docker compose up` 后 Milvus 连不上（降级 NumpyStore）；即便连上，播种向量实际 `row_count=0`（知识库空的）。

### 根因（4 个连锁问题）
1. **pymilvus 版本锁死 `<2.4.0`**：requirements.txt 写 `pymilvus>=2.3.0,<2.4.0`，装出 2.3.8。其 `MilvusClient` **没有 `flush` 方法**，而 `vectorstore.py` 的 `MilvusStore` 是按 `MilvusClient` 高级 API 写的（与开发环境 **pymilvus 3.0.1** 一致）。`insert` 后必须 `flush` 才落盘，缺 flush → 向量全丢。
   → 改 `requirements.txt`：`pymilvus>=3.0.1,<3.1.0`（注：`flush(collection_name:str)` 是 3.0.1 签名；2.4/2.5 是 `collection_names` 列表，别用）。
2. **逐条 flush 极慢**：`insert_batch` 每次都 `flush`，241 篇文档 = 241 次段封口，播种要 ~60min。
   → `insert_batch(records, flush=False)` 批量插入，播种末尾统一 `vs.flush()` 一次（~40s 完成）。
3. **MySQL 启动期 Connection refused traceback**：`_ensure_database`/`_get_mysql_conn` 的 `pymysql.connect` 无重试，MySQL 健康探针通过到真正接受连接有窗口，首连报 traceback（良性但污染日志）。
   → 加 `_mysql_connect_retry` 带退避重试（10 次）。
4. **多 worker 重复播种**：gunicorn 不开 `--preload` 时 4 worker 各导入一次 wsgi → 各自跑 `init_database()` 并发重复播种。
   → Dockerfile CMD 加 `--preload`（master 导入一次再 fork）。

### 其它配套
- Dockerfile.backend：PyPI 默认改 **阿里云镜像**（`PIP_INDEX_URL`，国内 ~10x 提速）；新增可选 `INSTALL_LOCAL_EMBED` 构建参数（装 torch+sentence-transformers 启用真 BGE 语义向量）。
- `.dockerignore` 已排除 `backend/data/models`（1.4GB HF 缓存，容器未装 sentence-transformers 用不上，且会拖慢构建）。
- compose：Milvus 加 healthcheck（9091/healthz）+ `backend depends_on milvus: service_healthy`，避免启动即降级；`OPENAI_EMBED_MODEL`/`RERANK_MODEL_PATH` 显式置空（避开 .env 里失效的本地模型路径）。
- **注意 `uploads_data` 空卷陷阱**：若命名卷已存在且为空，Docker 不会从镜像拷贝 241 篇文档 → 知识库为空。清卷重建须 `docker compose down -v` 且确认 `medical-assistant-master_uploads_data` 被真正删掉（有时需 `docker volume rm -f` 补刀）。

### 验证
`docker compose up -d --build` 后：后端 38s healthy；`/api/vector/status` 返回 `MilvusStore`；`get_collection_stats` 的 `row_count=241`；前端 `:3000` HTTP 200；全容器（backend/frontend/mysql/minio/attu）ERROR=0。Milvus 日志里的 `error=` 字段是启动期 INFO 噪声（如 create_collection 时 "collection not found"），非致命。
